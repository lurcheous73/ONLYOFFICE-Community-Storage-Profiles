# v0.3.4 — Manual backup hardening

Status: implementation branch. **Manual backup only.** Scheduled/nightly policy is deliberately deferred until the manual path passes a full real-data backup and controlled restore acceptance.

## Scope

v0.3.4 hardens the `S3Compatible` backup path without modifying the stock legacy `S3` consumer.

### Large streamed backups

- dedicated S3-compatible backup multipart part size: **192 MiB** (`201326592` bytes)
- S3 multipart maximum: 10,000 parts
- resulting theoretical object ceiling: about **1.83 TiB**
- design target: **at least 1.5 TiB** with useful headroom
- compressed TAR/GZIP data continues to be uploaded while the backup is being produced
- upload streams remain disk-backed via ONLYOFFICE `TempStream`; v0.3.4 does not create a complete local backup archive before upload
- bounded asynchronous upload queue, using at most half the logical CPUs and capped at 8 concurrent part uploads
- part 10,001 is rejected locally with an explicit capacity error before an invalid S3 request is sent
- any writer/upload/finalisation failure attempts `AbortMultipartUpload` before propagating the backup failure

The ordinary ONLYOFFICE file-upload chunk size is not changed.

### Manual bucket workflow

The manual Backup page adds a gated S3-compatible workflow:

1. select `S3Compatible` and provider profile;
2. enter/confirm endpoint, region and credentials;
3. **Check connection**;
4. list existing buckets when `ListBuckets` is permitted;
5. select an existing bucket, refresh the list, or explicitly create a new bucket;
6. **Validate bucket** with a disposable 100 KiB object;
7. only after successful validation is **Make Backup** enabled for `S3Compatible`.

Validation performs a complete round trip:

- PUT 100 KiB random payload;
- HEAD and size check;
- GET and SHA-256 comparison;
- DELETE;
- confirm the object is no longer present.

Test objects use `.onlyoffice-storage-test/validation-<uuid>.bin` and credentials are handled transiently by the authenticated Control Panel request. They are not written to the repository, state files or logs by the v0.3.4 code.

Changing provider, endpoint, region, credentials, path-style setting or bucket invalidates the prior validation and disables Make Backup again.

If an account is permitted to access a known bucket but cannot call `ListBuckets`, the UI exposes manual bucket entry and still requires the same write/read/delete validation before backup.

## Explicitly deferred

- scheduled/nightly backup enablement or policy changes;
- cron changes;
- automatic provider/bucket creation without an explicit user action;
- changing the stock `S3` consumer;
- primary Workspace storage migration;
- restore automation.

## Acceptance gates

Before scheduled/nightly behaviour is added:

1. installer/status/rollback pass;
2. existing v0.3.2 S3-compatible CRUD and multipart harness still passes;
3. Control Panel connection/list/create/select/100 KiB validation works against MEGA S4;
4. the real manual Workspace backup completes and the final backup object is visible in the selected bucket;
5. there is no outstanding failed multipart upload from the acceptance run;
6. backup history records the successful third-party-consumer backup;
7. a controlled restore acceptance is planned and performed separately before upstream production-ready claims.
